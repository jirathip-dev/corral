## Priority target: the `core/redact.rs` memoization

### Verdict on the memoization itself: CORRECT — no finding

The comment's argument is sound and I could not construct a counterexample.
Restating it precisely, because the informal version is slightly weaker than
what the code actually needs:

`high_entropy_at(input, i)` scans **forward only** — it evaluates the run
`[i, run_end)` where `run_end` is the first non-alphanumeric byte at or after
`i`. It never extends left. So for any `i' ∈ (i, run_end)`, the run it would
evaluate is exactly the suffix `[i', run_end)`: strictly shorter, and its
`lower`/`upper`/`digit` flags are a subset. Both failure modes of the
predicate (`len < 24`, or a missing class) are therefore monotone — a failed
run cannot succeed from any interior start. `entropy_cleared_until` is set to
exactly `run_end`, exclusive, so position `run_end` itself is still checked.

I specifically attacked the three angles the brief names:

1. **Interior entry via `i = end` after a prefix/env match.** The only matcher
   that can land `i` mid-alphanumeric-run is `PrefixKind::UpperDigit` (`AKIA`),
   whose scan stops at the first byte that is not uppercase-or-digit — which
   may be a lowercase letter, i.e. still alphanumeric (`AKIA…ABCDEFabcdef…`).
   `sk-ant-` (token chars) and `ghp_` (alnum) always stop on a non-alnum byte;
   `env_value_at` always ends at `\n` or EOF. In the `AKIA` case the landing
   position is interior to a run, but the suffix argument still holds, and the
   *old* code evaluated the identical suffix at that position. No divergence.
2. **Is `entropy_cleared_until` ever stale across span edges?** No, and the
   reason is stronger than the comment states: the variable is *strictly
   monotone increasing* by construction — it is only assigned inside
   `if i >= entropy_cleared_until`, and the assigned value is
   `run_end.max(i+1) >= i+1 > i >= old value`. It can therefore never be
   "ahead" of a position it has not justified. Separately, every byte in the
   cleared range `[i, run_end)` is alphanumeric, so no *new* run can begin
   inside it — any span that starts and ends inside the cleared range ends at
   a position that is still a suffix of the same failed run.
3. **Token-glued runs, span-edge boundaries, UTF-8 multibyte neighbours.**
   Covered by the fuzzing below. Note the memo is byte-indexed but only ever
   set to `run_end` computed with `is_ascii_alphanumeric()`, which is false for
   every byte of a multibyte UTF-8 sequence (all ≥ 0x80), so a multibyte
   neighbour terminates the run like any other separator. No index can land
   inside a codepoint via this path.

### Differential verification (not just argument)

Model validated first against the module's own documented behaviors
(`sk-ant-` bare prefix kept, `mysk-ant-abc` passes, `delete-ghp_yyy`
redacted, `set debug key=false` / `?token=abc&a=1` untouched,
`API_KEY=xyz` → name kept, 64-char lowercase run kept, mixed run redacted) —
all matched.

- **Exhaustive**: every string of length ≤ 8 over the alphabet
  `a A 1 _ - = ␠ \n` — 19,173,960 inputs — with `HIGH_ENTROPY_MIN_LEN` and
  `ENV_VALUE_MIN_LEN` scaled down (3 and 2) so that matching runs, span
  merges and span edges are actually reachable at those lengths. The memo
  logic is threshold-independent, so this exercises the real control flow.
  **0 differences.**
- **Random, real thresholds**: 400,000 strings of length ≤ 14 over an
  alphabet including `sk-ant-`, `ghp_`, `AKIA`, `TOKEN`, `KEY`, `Ab1` and
  multibyte `é`/`中`. **0 differences.**
- **Targeted, real thresholds**: 300,000 strings assembled from
  full-length `AKIA`/`ghp_`/`sk-ant-` tokens glued directly to 30–40 char
  runs of each character class, env-assignment fragments, and multibyte
  neighbours — i.e. exactly the "entered mid-way via `i = end`" and
  "span-edge" shapes. **0 differences.**

**Answer to the brief's question "does the fix change ANY existing redaction
outcome?" — No.** Across ~19.9M inputs including every adversarial shape I
could name, pre- and post-diff output is byte-identical. This is a
behavior-preserving optimisation.

### The 1.5s debug bound: sane

Post-fix the 64 KiB blob is a single linear pass (my model counts 11,999
byte-steps for a 4 KiB blob vs 8,005,999 pre-fix — 3n vs ~n²/2). At 64 KiB
that is ~196k byte-steps: even a heavily loaded debug CI machine is ~3 orders
of magnitude inside 1500 ms, while a re-introduced quadratic would be
~2.1×10⁹ steps and blow the bound by a wide margin. The bound discriminates
correctly and is not flake-prone. One caveat, not a finding: the assertion
measures wall-clock inside a `cargo test` run that executes tests in
parallel, so it is a *shared-resource* timing assertion of the same family as
the `git_plane` flake the report itself observed. Since the headroom is ~150×
rather than ~2×, I judge it acceptable as written.

## Findings

### F1 — HIGH (blocking): `read_jsonl_page` never terminates on a transcript containing a line ≥ 512 KiB
`src/transcript/mod.rs:392-401` (resume computation), with `:354` (`first_consumable`).

The `!stopped_early && lower > 0` branch sets
`resume = lines[first_consumable].start`. When the scan range contains exactly
one `\n` and that `\n` is the last byte of the range, `buf.split(b'\n')`
yields two segments: the partial line (skipped as `first_consumable`) and a
**trailing empty segment whose absolute start is `end` itself**. That empty
segment is whitespace-only, so the loop `continue`s over it, `stopped_early`
stays false, and `resume == end`. `next_cursor` is then `Bytes { offset: end }`
— **the same cursor that was passed in**. `read_jsonl_page` is a pure function
of `(file, cursor, limit)`, so the caller loops forever on empty pages.

Trigger condition: any line of ≥ `scan_cap - 1` = 524,287 bytes that is not
within the first `scan_cap` bytes of the file. That is not exotic — a single
large tool result or paste in a `~/.claude` JSONL transcript exceeds 512 KiB
routinely. The walk is *guaranteed* to reach the trigger offset, because
`resume` is always the start of the oldest line consumed, and the line
immediately after the giant line will be the oldest consumed in some page;
its start is exactly `giant_newline_offset + 1`.

Reproduced by simulating the exact offset arithmetic (scratchpad model, no
repo change): file = 5 normal lines + one 525,321-byte line + 3 normal lines
(525,594 bytes total).

```
page  0: cursor_in=None    entries=3 skipped=0 cursor_out=525492
page  1: cursor_in=525492  entries=0 skipped=0 cursor_out=525492
*** cursor did not advance ***
```

The five oldest entries are also unreachable, and `skipped` stays 0 — the page
reports a clean read while looping.

The module doc at `:295-305` asserts "every call stays bounded and the walk
stays complete". Each call is bounded; the walk is not.

Minimal fix: the resume offset must be proven to strictly decrease —
e.g. `.filter(|r| *r < end)` before building `next_cursor`, plus a decision on
what to do with the over-long line (see F8) rather than silently stalling.
The existing `walk()` test helper already has `assert!(pages < 1000)`, so a
fixture with one >512 KiB line would have caught this; no test builds one
(the budget test's lines are 64 KiB).

### F2 — HIGH (blocking): opencode keyset cursor is not unique over the joined rows, so message parts are silently dropped
`src/transcript/mod.rs:186-203` (SQL), `:268-289` (cursor derivation).

The SQL `LEFT JOIN part p ON p.message_id = m.id` emits **one row per part**,
but `LIMIT` bounds join rows while the cursor keys only on
`(m.time_created, m.id)` — which is *not* unique across those rows. The next
page's predicate is strict (`m.time_created < t OR (= t AND m.id < id)`), so
when a page boundary lands inside a multi-part message, **every remaining part
of that message is excluded from every subsequent page**. The report's claim of
"strict `(time_created, id)` descending keyset pagination" does not hold: keyset
pagination requires the key to be unique over the result set.

Verified against a scratch fixture (not a live store) using the module's exact
SQL. Session `ses1`: `m3`(1 reasoning part), `m2`(text A, tool, text C),
`m1`(1 text part) — 5 join rows. Walking with `limit=2` as `read_opencode_page`
does (cursor = last **consumed** row = `(200,'m2')`):

```
page 1 rows: m3/reasoning, m2/"part A of the answer"   -> cursor (200,'m2')
page 2 rows: m1/"question one"                          -> exhausted
```

`"part C of the answer"` — a real assistant text part — is **never emitted**,
and both pages report `skipped == 0`, so the transcript looks complete. With
`limit = MAX_PAGE_ENTRIES = 50`, any message with more than 50 parts loses the
tail unconditionally, and any message straddling a page boundary loses whatever
did not fit.

Two aggravating factors:
- Among rows sharing `(time_created, id)` the `ORDER BY` imposes **no**
  ordering on parts, so *which* parts survive is at SQLite's discretion and may
  differ between runs — the loss is nondeterministic.
- The intended entry shape is undecided and inconsistent across stores: the
  JSONL reader joins all text parts of one message into **one** `Entry`
  (`:427-440`), while the opencode reader emits **N** entries for N parts, each
  repeating the same `role`/`ts`. Whatever the intended shape, the two readers
  should agree; a UI cannot render both.

The fixture test at `:653-703` inserts exactly one part per message, so this
entire class is untested.

Fix direction: aggregate parts in SQL (`group_concat` over `p.type='text'`
with a deterministic `ORDER BY p.id`) so one row = one message and the keyset
key is unique again; or page on a genuinely unique key (`m.id, p.id`). Either
way, add `p.type = 'text'` filtering (see F6) and a deterministic part order.

### F3 — MEDIUM-HIGH: the O(n²) fix is incomplete — `env_value_at` is still quadratic, on the same inputs the diff exists to make fast
`src/core/redact.rs:223-245`, notably the end-of-line scan at `:235-238` and the
whitespace scan at `:241`.

`env_value_at` runs *before* the memoized entropy check and is not memoized.
At every identifier start whose name is secret-ish and is followed by `=`, it
scans `k` forward to the end of the **line** and then scans the value again for
whitespace — then throws that work away when the shape gate rejects. Reject is
the common case for prose: `name_is_env_shaped` is false for a bare
`key`/`api`/`token`/`auth`/`secret`, and a rest-of-line value containing a space
fails the token test. So on a long single line carrying many such names, the
cost is O(occurrences × line length).

Measured with the byte-faithful model (byte-steps, input `"key=a "` repeated):

```
len   3000   post-fix ops     1,504,000   pre-fix ops     1,503,500
len   6000   post-fix ops     6,008,000   pre-fix ops     6,007,000
len  12000   post-fix ops    24,016,000   pre-fix ops    24,014,000
len  24000   post-fix ops    96,032,000   pre-fix ops    96,028,000
```

Exactly quadratic, and **the diff changes nothing** (96,032,000 vs 96,028,000).
Contrast the shape that *was* fixed, where the same counter goes 8,005,999 →
11,999 at 4 KiB. Extrapolating ≈ n²/6: a single 256 KiB `MAX_PAGE_TEXT_BYTES`
blob of this shape is ≈ 1.1×10¹⁰ byte-steps, and a JSONL line may be up to
`scan_cap` = 512 KiB (≈ 4.6×10¹⁰) — i.e. *worse than the 35 s the diff set out
to eliminate*, and AC3 (<2 s) is still unreachable.

This is pre-existing code, but **this diff is what makes it reachable**: before
#62, `redact()` saw short pane text; `jsonl_entry` (`:452`) now hands it
whole-line transcript blobs, unbounded up to 512 KiB, before any budget check.
Realistic triggers are ordinary transcript content: a one-line list of URLs
carrying `?api=…`/`&key=…`/`&token=…` (the `?`/`&` are not identifier chars, so
each is an identifier start), or a long command line of `--key=v` flags.

The regression test at `:549-578` pins only the entropy shape, so it will stay
green while this path is quadratic. Fix: hoist the line-end scan (compute the
current line's end once per line, or evaluate the cheap `name_is_env_shaped`
gate before scanning to EOL). Add a second perf pin for the `key=…` shape.

### F4 — MEDIUM: `Entry.role` crosses the module boundary unredacted and outside the page byte budget
`src/transcript/mod.rs:417-422` and `:451` (JSONL), `:249-258` and `:274`
(opencode).

The module header (`:4-6`) states: "with every entry redacted (D-083 rules) …
BEFORE it leaves this module — no unredacted text crosses the boundary."
`text` is redacted; `role` is not. `role` is taken verbatim from
`message.role` / the top-level `type` field of an externally-written JSONL file,
or from `m.role` / `msg_data.role` in the opencode DB. Those are
attacker-influenceable strings — the stores are written by other tools, and the
brief is right to ask: judged, they are untrusted input, not a closed enum. The
code never validates `role` against `{user, assistant, system, …}`.

Second, independent problem: `MAX_PAGE_TEXT_BYTES` is charged against
`text.len()` only (`:376`, `:266-270`). A `role` string is unbounded, so a page
of 50 entries can carry up to 50 × (line size) of role text — ~25 MB for JSONL,
**unbounded** for opencode where `m.role` has no length limit. The documented
256 KiB page cap is not enforced on the data actually returned.

Fix: `redact(&role)`, and either charge `role.len()` to the budget or clamp
`role` to a small maximum / map unknown values to `"unknown"` (the opencode path
already has an `"unknown"` fallback at `:258`).

### F5 — MEDIUM: the opencode query has no wall-clock timeout, contrary to the pattern it claims to mirror
`src/transcript/mod.rs:206-227`, vs `src/cost/opencode.rs:132-149`.

The module doc (`:9-19`) says the reader uses "the same sqlite3-CLI pattern as
`crate::cost::opencode` — `-readonly`, busy timeout, JSON output, every query
bounded". It drops one element of that pattern: `cost::opencode` wraps the
spawn in `tokio::time::timeout(QUERY_TIMEOUT, fut)`; `read_opencode_page`
awaits `.output()` with **no deadline**. `.timeout 2000` is SQLite's *busy*
timeout — how long a statement waits on a write lock — not a cap on execution.

On the 13 GB steady-state store this matters: `LIMIT` bounds the *result*, not
the *scan*. `WHERE m.session_id = ?` needs an index on `message.session_id`,
and `LEFT JOIN part p ON p.message_id = m.id` needs one on `part.message_id`;
absent either, SQLite scans. Nothing in the diff feature-detects or asserts
those indexes (unlike the schema feature-detection the doc credits the cost
reader with), so a hung/long query hangs `read_page` indefinitely with no
recovery. Restore the `tokio::time::timeout` wrapper.

### F6 — MEDIUM: an all-malformed opencode page reports exhaustion and truncates the walk
`src/transcript/mod.rs:283-292`.

`last_key` is only assigned for *accepted* rows (`:272`). If every row in a
full `LIMIT`-sized batch fails the `(id, time_created)` extraction at
`:243-249`, `last_key` stays `None`, so `match (&last_key, …)` falls through to
`_ => None`: `next_cursor` is `None` and the caller concludes the session is
exhausted, while every older message is still there and unread. The `skipped`
counter says `50` but the page also says "done", which is a contradiction the
type cannot express.

Reachability is not hypothetical: `Value::as_i64` returns `None` for a JSON
*float*, and the sqlite3 CLI emits a REAL column as a float. If the live
`message.time_created` is REAL or TEXT rather than the INTEGER the fixture
declares (`:658`), **every** row is skipped and the reader returns an empty
transcript for every session while reporting success. The report acknowledges
"slice 2 revalidates against live stores"; until then the failure mode is
silent-empty rather than a typed error, which is the wrong direction.

Related, lower-impact: when the *last* row of a page is skipped, `last_key`
points at an older... newer accepted row, so the skipped row is re-fetched and
re-counted on the next page — `skipped` double-counts across a walk.

Fix: track the last row's `(time_created, id)` for cursor purposes
independently of whether the row produced an entry, and surface an all-skipped
full page as an error rather than as exhaustion.

### F7 — MEDIUM: non-text opencode parts become empty entries that consume the page limit
`src/transcript/mod.rs:260-278`.

The SQL does not filter `p.type`, and the extraction at `:260-265` ends in
`.unwrap_or_default()`. A part with no `text` key — `tool`, `reasoning`,
`step-start`, or a message with no parts at all (the `LEFT JOIN`'s NULL row) —
therefore yields `Entry { role, text: "", ts }`, pushed unconditionally at
`:273`. Confirmed on the scratch fixture: the reasoning part of `m3` returns
`part_data = {"summary":"thinking"}` and the reader emits an entry with empty
text.

Consequence: a page of `limit` entries can be entirely blank, and `skipped`
stays 0 so nothing signals it. For a session whose recent messages are
tool-heavy — the normal case — the newest page renders empty. Add
`AND (p.type = 'text' OR p.id IS NULL)` in SQL, or skip empty text in Rust
(and decide deliberately whether an empty message should count as `skipped`).

### F8 — MEDIUM: `skipped` counts ordinary, well-formed non-message records, so the honesty counter is noise
`src/transcript/mod.rs:409-416` (doc), `:443-445` (the `None`), `:369-372` (the
count).

`jsonl_entry` returns `None` whenever the extracted text is empty, and the
caller counts every `None` as `skipped`. But `None` is also the correct answer
for a large class of *perfectly valid* records that real claude transcripts are
full of: `{"type":"summary",…}`, file-history snapshots, and — importantly —
any assistant turn whose `content` array holds only `tool_use`/`tool_result`
parts (`:427-437` only harvests `part.text`). Those all take the
`text.is_empty()` path.

`TranscriptPage::skipped` is documented at `:87-90` as "malformed lines/rows …
a nonzero value means the page is complete but the store had torn data in this
range". On a healthy claude transcript it will be large and constant, so any UI
or alert built on it reports permanent corruption. Either separate
"unparseable" from "not a transcript-bearing record" into two counters, or
narrow `skipped` to genuine parse failures.

The test at `:576-591` only feeds genuinely-broken lines, so it pins the
counter's value without pinning its *meaning*.

### F9 — LOW-MEDIUM: a JSONL line larger than `scan_cap` is permanently unreadable
`src/transcript/mod.rs:334-356`.

Same root cause as F1, distinct symptom, and it needs its own decision. A line
longer than `scan_cap` (512 KiB) can never be materialised: the range always
starts inside it, so it is either `lines[0]` (dropped as the partial-line
boundary) or a truncated head that fails to parse and is counted `skipped`.
Meanwhile each call steps `end` back by only `scan_cap`, so the walk emits one
empty page per 512 KiB of the oversized line before it gets past it (if F1 is
fixed; today it stalls instead).

This contradicts the deliberate design elsewhere: `:374-379` explicitly lets a
single oversized entry through alone rather than drop it ("never drops"). That
promise stops at 512 KiB with no error and no counter distinguishing it from a
torn line. Either grow the range when a range yields no line boundary, or
return a typed error/marker entry so the caller knows content was skipped.

### F10 — LOW: `ts` handling — sign wrap, and the ordering test's fixture shape does not exist in real claude transcripts
`src/transcript/mod.rs:276` and `:446-449`, test at `:462-470`/`:617-634`.

- `ts: Some(t as u64)` wraps a negative `time_created` to a value near
  `u64::MAX` rather than rejecting it. Cheap to fix: `u64::try_from(t).ok()`.
- `jsonl_entry` reads `ts` / `timestamp` via `Value::as_u64`. Real Claude Code
  transcripts carry `"timestamp"` as an **ISO-8601 string**, which `as_u64`
  rejects, so `ts` is `None` for every entry from the store this reader
  primarily targets. The `ts: Option` deviation is defensible (see below), but
  the consequence is that the fixture helper `claude_line` (`:462`) invents a
  numeric `"ts"` field that the real format does not have, and
  `jsonl_walk_is_newest_first_complete_and_duplicate_free` (`:617`) asserts
  ordering **using that invented field**. The ordering property is therefore
  pinned only for a synthetic shape. A fixture derived from the real record
  shape (ISO `timestamp`) would assert ordering on entry *text*, which is what
  a real caller sees.

### F11 — LOW: `db_path` is passed through lossy `Display` instead of as an `OsStr`
`src/transcript/mod.rs:170-180`.

`opencode_sqlite_args` returns `Vec<String>` and builds the path element with
`db_path.display().to_string()`. `Display` is lossy: non-UTF-8 path bytes
become U+FFFD, so the reader silently opens the wrong path (or fails) instead
of working. `cost::opencode` avoids this by passing `.arg(db_path)` directly.
The argv-pinning test (`:637-644`) is the reason for the `Vec<String>` shape;
`Vec<OsString>` would pin equally well.

### F12 — NIT: an unedited self-correction ships as documentation
`src/transcript/mod.rs:409-416`.

> "counted as skipped by the caller only when unparseable — a parseable
> non-message line is silently ignored... no: counted skipped too, so pages
> stay honest about what they passed over"

A doc comment in a security-adjacent module that argues with itself mid-
sentence. State the resolved behavior (and fix it per F8).

### F13 — NIT: two small looseness items
- `have_sqlite3()` (`:646-651`) uses `.output().is_ok()`, which is true whenever
  the binary *spawns*, regardless of exit status; it does not verify a usable
  sqlite3. Harmless for a skip-guard, misleading as a name.
- `read_page` (`:150`) silently rewrites `limit = 0` to `1` via
  `clamp(1, MAX_PAGE_ENTRIES)`. Fine as a policy, undocumented in the rustdoc,
  which only mentions clamping to the maximum.

## Questions from the brief, answered explicitly

### SQL injection via `session_id` / cursor id — NOT a defect
`src/transcript/mod.rs:186-204`. Doubling `'` **is** the complete and only
escaping rule for a SQLite string literal: SQLite has no backslash escape, and
`--`, `/*`, newline, `;` and every other byte are inert inside a quoted
literal. The SQL is passed as a single `argv` element to `sqlite3` with no
shell, so shell metacharacters are irrelevant. `time_created` and `limit` are
interpolated from `i64`/`usize`, which cannot produce injection.

The two inputs the brief names specifically:
- **Newline** — safe. A raw newline inside a SQLite string literal is a
  literal newline; it cannot terminate the statement.
- **NUL** — safe, but yields a misleading error. Rust's `Command` rejects an
  argument containing an interior NUL at spawn time, and `:213-215` maps *any*
  spawn error to `TranscriptError::Sqlite3Unavailable`. So a session id with an
  embedded NUL reports "the sqlite3 binary is unavailable", which will send
  whoever debugs it in the wrong direction. Worth a `BadCursor`-style validation
  of `session_id`, but it is not a security hole.

The quoting test at `:648-655` pins the escaping correctly.

### Cursor stability when two opencode messages share `time_created` — sound
The tiebreak `(m.time_created = t AND m.id < id)` matches the
`ORDER BY m.time_created DESC, m.id DESC` exactly, and `m.id` is the table's
PRIMARY KEY, so ties on `time_created` are broken by a unique, order-consistent
key with the same collation in both clauses. No duplicates and no skips from
that direction. The keyset breaks for an unrelated reason — the join makes the
key non-unique over the *result rows* — which is F2, not a tie-break problem.

### Redaction-before-boundary — one escape found
`text` is redacted on every path (`:452` for JSONL, `:266` for opencode); I
found no path where `Entry.text` escapes unredacted. `Entry.role` does escape
unredacted — F4. `Entry` derives no `Serialize` today, so nothing outside the
crate can emit it yet; that is timing, not a guarantee, and #63/#64 will add
the HTTP surface. Fix it here while the boundary is still one module.

### JSONL pager boundary cases — enumerated
Verified by modelling the exact offset arithmetic:
- line starting exactly at `lower` — **safe**: it is dropped as
  `first_consumable` and re-read in full on the next call. One line of wasted
  work per page, no loss, no duplicate.
- file not ending in a newline — **safe**: the final segment is the last line
  and is consumed normally.
- CRLF — **handled** at `:363` (`strip_suffix(b"\r")`), untested.
- empty lines — **safe**: whitespace-only segments advance
  `oldest_consumed_start` without being counted as skipped.
- `cursor == 0` — **safe**: early return, exhausted (`:325-331`).
- `cursor == len` — **safe**: identical to `None`.
- `cursor` mid-line — **safe but lossy**: the truncated line fails to parse and
  is counted `skipped`. Only reachable if a caller fabricates an offset; the
  module never emits one.
- wrong cursor *variant* for the store kind — correctly rejected as
  `BadCursor` (`:157-159`, `:320-323`); untested.
- **can the walk loop forever?** — **YES**, see F1.
- **can a line straddling the scan-cap boundary be dropped?** — not by the
  boundary logic (it is re-read next call); yes by size, see F9.

### F1 — the stride: does `resume` strictly decrease in every branch? YES

Re-derived per branch, then measured.

- `stopped_early` → `resume = oldest_consumed_start`. Both break sites run
  *after* at least one push (the budget break is guarded by
  `!entries.is_empty()`), and a pushed segment is non-whitespace, so it can
  never be the trailing empty segment at `end`. Therefore `r < end`. ✓
- `!stopped_early && lower > 0`, `lines.len() > first_consumable` →
  `r = lines[1].start ≤ end`; the `r >= end` arm now catches the equality case
  and replaces it with `lower`, and `lower = end - scan_cap < end` because this
  branch requires `lower > 0`. ✓
- `!stopped_early && lower > 0`, `lines.len() <= 1` → `map_or(lower)` →
  `lower < end`. ✓
- `lower == 0` → `None`, terminates. ✓

Measured against the round-1 repro and beyond:

### F3 — re-derived: is the accept set byte-identical?

Yes. Full case split, then measured.

- **Env-shaped name**: old scanned to EOL and could not be rejected by the gate
  (`!name_is_env_shaped && …` short-circuits false); new scans to EOL and
  returns the same span under the same `k > j+1` test. Identical.
- **Non-env-shaped, no whitespace before EOF** (`k_ws == len`): `\n` *is* ASCII
  whitespace, so no newline exists either and `k_eol == len == k_ws`. Old
  accepted iff `len ≥ 8` and no whitespace — both hold by construction. Same.
- **Non-env-shaped, first whitespace is `\n`**: every byte in `[j+1, k_ws)` is
  non-whitespace hence not `\n`, so `k_eol == k_ws` and the value is
  whitespace-free. Both accept iff `len ≥ 8`. Same.
- **Non-env-shaped, first whitespace is not `\n`**: new rejects immediately.
  Old built a rest-of-line value that necessarily *contains* that whitespace
  byte (`k_eol > k_ws`), so `value.bytes().any(is_ascii_whitespace)` was true
  and old rejected too. Same. **This is exactly the implication the report
  claims, and it holds.**

Both implementations use the same `is_ascii_whitespace` predicate, so the
vertical-tab (`\x0b`) exclusion is consistent across the change — a detail an
independent reimplementation would plausibly have got wrong.

Empirically: 200,000 randomised strings built from fragments that reach every

`ab cd`, and separators `\t \r \n \x0b \x0c . & ? -`), compared **at every byte
position** — **2,385,710 positions, 0 divergences.**
